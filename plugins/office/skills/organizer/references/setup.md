# Setup

A prompt-driven setup, not a script: explore, present what you found, ask, then write. Idempotent: a rerun adds what is missing and brings every installed section prompt up to its template: the template's current text, with the project's own parts kept (its "Wants" and additions). A prompt with no template, written with the user, stays as it is. Show each prompt's diff before writing it.

## 1. Explore

Read what exists; assume nothing:
- the project's `CLAUDE.md` / `AGENTS.md` files and `git remote -v`: where meeting notes live, how work splits into tracks, which language the user wants, rules for outgoing messages
- what this session can reach: connected MCP servers, plugins, CLIs, and whether Claude Desktop's `scheduled-tasks` tools load (ToolSearch)
- `.claude/organizer/`: an earlier setup's config and section prompts
- any earlier dashboard, filter list or scheduled routine in the project or in Desktop that this one could reuse or join
- in the tracker, once the storage mode is chosen (below): what the storage reference's Setup lists, each checked as it says

## 2. Present and ask

Summarise what is there and what is missing. Then go section by section, one answer at a time, leading with your recommendation so the user can accept it in a word; skip what exploration already settled.

- **Sections.** Recommend `meetings`, `prs` and `tasks`, the templates in this skill's `sections/`. Another section gets a prompt written with the user in the same shape. A section id is never `setup`: `sync <word>` reads the word as a section id. When two sections could collect the same matter, ask which owns it, and write into the other's prompt what it leaves to the owner: collectors run in parallel and do not see each other's cards.
- **Tracks.** The areas the project splits its work into, from its `CLAUDE.md`; recommend them as the `tracks` list. Sections and digest topics name tracks only from it.
- **Sources**, one AskUserQuestion per topic (`multiSelect`, only the reachable sources that fit, free text for the rest): where the meetings and their notes are, where the pull requests are (host, workspace, repos), where open tasks and threads waiting on the user are. Each chosen source is declared once, as in [Sources](#sources), however many sections want it.
- **Gaps.** For each fact a section needs that the project does not state (where meeting notes live, the track split, the language), recommend its one home: the project's `CLAUDE.md` when other work also needs it (show the draft, write it on a yes), else the section's prompt. A preference about what a section's cards say (what to stress for which team) goes into that section's prompt.
- **Storage mode:** a built-in one, `github` or `artifact-db`, the references in `storage/`, or `custom` for a store the user names; see [tracker.md](tracker.md). The cards hold private matter (meeting names with client names, decisions, who owes what, links to private mail), so put into the question who can read each store: `artifact-db` is personal, only its owner reads it, and needs only this Artifact tool; `github` keeps the cards as issues in a repo that everyone with access to that repo reads, meetings long over included. That repo need not be the project's: in the project's own repo the whole team reads the user's cards, while a repo made for the cards alone, with no one else in it, is as personal as `artifact-db`. Recommend `github` when the user names such a repo and its connector is reachable, else `artifact-db`. For `custom`, learn how that store does each contract operation and write `.claude/organizer/custom-storage.md` in the sections [tracker.md](tracker.md#other-storage-modes) lists (an empty one says "none"), opening with the line "Storage mode outside the built-in ones, behaviour not guaranteed." Done when every section is there and Operations has a row for every operation in [tracker.md](tracker.md#operations). From here on, the **storage reference** is that file or `storage/<storage>.md`.
- **Page settings:** the tracker settings its storage reference's Setup lists, the title, the reply signature, the PR filters (authors, repos), and the **Theme**: recommend the config's current Theme, else this skill's default; the other answers are a Refero style, any DESIGN.md link, or a local or pasted DESIGN.md, each turned into a Theme as in [Theme](#theme).
- **Agent assignee:** the tracker account agent tasks are assigned to and the sync takes them for ([comments.md](comments.md#agent-tasks)), in the form and with the recommendation the storage reference's Setup gives; a bot account fits once there is one. Each person or bot sharing the tracker sets its own, so each run takes only its own cards.
- **Assistant tools.** List the connectors this session has, with their tools, and ask which the Assistant gets (`multiSelect`, tracker-related tools first: the issue tracker the project uses, then mail, chat, calendar). One `sample` call takes at most 16 tools and the page's own take up to 9 on a card (tasks, comments, ✓ / ✕ / ⏸, repo reads), so recommend at most 7; say which would be cut. The tracker's connector is never on this list: the page reaches it only through its own tools. **Repo reads** are set separately, by job, from the repo host's connector: read one file, search code, list branches, list commits; each becomes a `{server, tool}` entry under `[assistant.repo]`.
- **Assistant branch:** which branch its repo reads go to: `last-active` (recommended: the branch with the newest commit, worked out when the page opens), a branch name, or `ask` (the assistant asks in the chat). The user can switch it in the chat either way.
- **Project folder:** the local folder «Open in Claude Code» opens (a long Cloud task past its step cap continues there). Ask for the absolute path of the project on this machine, recommend the current working directory, and save it as `project-folder`; empty is allowed (the link then opens without a folder).
- **AI marker:** the text the project's rules put on messages Claude drafts or sends (from its `CLAUDE.md` when it says; else ask). When the rules give several forms (one for drafts, one for sends), `ai-marker` is the part they share. A connector write without it is refused by the page.

## 3. Write

1. **Config** in `.claude/organizer/`:
   - one prompt per section in `sections/`, copied from the template with its "Wants" filled in;
   - one `[[source]]` entry and one `sources/<id>.md` per source, as in [Sources](#sources);
   - `[intake] prompt = "intake.md"` and that file, written with the user: where transcripts, their log, the meeting notes and the daily brief live, which transcript sources exist, routing rules, what mail to leave out, the note format ([intake.md](intake.md) says what each must settle); a project with no meeting notes skips it;
   - `organizer.toml`: `storage` (a built-in name or `custom`), `title`, `artifact-url`, the tracker settings from the storage reference's Setup, `reply-signature`, `poll-seconds` (60), `stale-hours` (26: the page warns when no run has written the status record for that long), `task-section` (the `[[section]]` id the Assistant's new tasks go to: the one built from the `tasks` template), `ai-marker`, `agent-assignee`, `project-folder`, `[assistant]` (`branch`, and `tools` as `{server, tool}` entries in the order the user chose) with `[assistant.repo]` (`read_file`, `search_code`, `list_branches`, `list_commits`, each a `{server, tool}`), `tracks` (the list of track labels), `[meetings]` (`window-days`, `full-brief-working-days`), `[labels]` (`tasks`, `subtasks`: the words on the «Tasks: N» and «Subtasks: N» buttons, in the user's language; left out, they read `Tasks` and `Subtasks`), one `[[source]]` each (`id`, `tools`, `prompt`) and one `[[section]]` each (`id`, `title`, `prompt`, `card-actions`, optional `[section.filters]` with `authors` and `repos`);
   - author avatars, if the user has them, as `avatars/<name>.png`;
   - `theme.css` and `DESIGN.md`, the page's **Theme** and its **Style source**: the pair the Theme question produced; with no new answer, the folder's pair stays as it is, and a folder with none gets this skill's default `theme.css` and `DESIGN.md`.
2. **Tracker.** Do the storage reference's Setup: it names what to create, and whether before or after the page is published (step 4).
3. **Page.** The page is six files: this skill's `page.html`, `base.css`, `logic.js`, `tracker.js`, `app.js`, and the config's `theme.css`. Copy all six into one scratch folder outside the repo; the steps below change only the copies. Fill `page.html`: replace `__ORGANIZER_CONFIG__` with this JSON, every `<` written as the JSON escape `\u003c` (so a `</script>` inside can not end the page script):
   `{"title", "storage", "repo", "server", "replySignature", "pollSeconds", "staleHours", "taskSection", "aiMarker", "agentAssignee", "projectFolder", "buttonWords": {"tasks", "subtasks"} (from `[labels]`), "assistant": {"branch", "tools": [{"server", "tool"}], "repo": {"<job>": {"server", "tool"}}}, "rules", "sections": [{"id", "title", "cardActions", "filters"}]}`, read from `organizer.toml` (`filters` exactly as written there; `server` in `assistant.tools` is the connector's display name; `storage` picks the page's tracker, `github` or `artifact-db`, and the page reads no other). `rules` is the Assistant's rules turn: the text of [assistant.md](assistant.md) as it is. Its UTF-8 size must stay far below `sample.limits()` `maxPromptBytes` (256 KiB), since the page trims the chat history to half that cap: check it with `wc -c` and report it. When the user's language is not English, translate the page's own strings (title, tabs, mode names, the theme switcher, buttons, `aria-label`s, placeholders, banners, error and empty states) into it: they sit in `page.html` and `app.js`, except the task-count words, which come from `[labels]`. `logic.js` stays in English: its `Brief`, `Prepare`, … are the card headings it parses.
4. **Publish** with the Artifact tool: `read` the URL in `artifact-url` first and build on what it returns, then publish in place to it (the link stays the same): `file_path` the filled `page.html`, and `files` mapping `base.css`, `theme.css`, `logic.js`, `tracker.js`, `app.js` from the scratch folder and every `avatars/<name>.png`, each at that bare relative path (the page loads `app.js`, not `/app.js`), with these capabilities, on every publish:
   ```json
   {"mcp": {"servers": [<the tracker's entry from the storage reference's Setup, if it names one>, <one entry per other server in [assistant] tools, with only its chosen tools>; the repo host's connector with the tools in [assistant.repo], when it is not the tracker's]}, "sample": {}, "db": <the storage reference's `db` rules, else {}>}
   ```
   The set is the whole declaration: one left out is revoked. `db` keeps the Cloud conversations (`cloud/tab`, `cloud/card-<n>`), shared by every viewer of the page, and in artifact-db mode the tracker's `records/`.
   No `artifact-url` yet: publish a new artifact with `icon: "calendar"` and write its URL back to `organizer.toml`. No Artifact tool in this session: say so and go on.
5. **Schedule.** Routines need Claude Desktop's `scheduled-tasks` tools. Without them, recommend rerunning setup from Desktop or print the routine for the user to add by hand. With them, offer to install and do it on a yes, skipping a routine some task's prompt already runs; a separate daily routine that writes the same notes (a digest) is retired in the same change, so no hour has two writers:
   - **Sync:** one task, `organizer-update`, running `/office:organizer sync` hourly (`0 * * * *`). Every Sync run is change-driven, so a quiet hour costs one cheap check per source.
   - **Permissions:** unattended runs stall on a prompt; name the tools the runs use so the user can allow them, as the storage reference's Setup says.
   - **Notifications:** Desktop shows a "task complete" banner after every run, several when a run ends more than one turn, and it can only be turned off for all sessions. Runs push on their own when something needs the user or fails, so offer to set `task_complete_notifications` to off (ccd_settings), saying it also silences the user's interactive sessions finishing.

## 4. Done

Offer to run the first `/office:organizer sync` now, so the page does not open empty; run it on a yes. In artifact-db mode, run it without asking: setup is done only when one Sync run finishes without errors. Report what was created, what already existed, and the page link. Then tell the user how to live with it:
- **Cloud and Local:** every card and the Assistant tab end with two parts. **Cloud** is a chat with Claude in the page: it answers, reads the repo on the chosen branch and the chosen connectors, and changes something (a task, a comment, ✓ / ✕ / ⏸, a draft) only when asked; a draft or message waits for a click on its preview. The last conversation stays until **New conversation**. It runs on the viewer's Claude plan, only while the page is open; claude.ai asks once to allow Claude for the page. **Local** is the card's comments, for work that needs the user's machine; on the Assistant tab it creates an agent task, which the sync claims, carries out and reports on in the card's comments.
- **Comments on cards:** a comment, written on the page or straight in the tracker, is a prompt for the next sync, which acts on it with local tools (notes, repo, messages) and answers with one signed reply in the same thread, within the hour. The page itself never answers comments.
- **What runs:** one sync every hour answers comments and updates the cards whose sources changed since the last run, only while Desktop is open. In github mode, the first time the page opens, claude.ai asks once to allow the tracker's connector.
- **Where problems show:** a banner on the page from the status record, a warning when no run has written it for `stale-hours`, and one push per new problem.
- **What to tune:** a section's prompt in `.claude/organizer/sections/` for what it collects and how; `organizer.toml` for filters, window and signature; the project's `CLAUDE.md` for facts other work shares. A comment on a card for a one-off.
- **When to rerun setup:** a new section or source, a new tracker, or a lost page; `/office:organizer setup <what to change>` for one change, e.g. `setup make the theme lighter`.

## Targeted setup

`/office:organizer setup <text>` (e.g. `make the theme lighter`, `add a section`, `add a source to the prs section`) runs only the steps the text touches. Explore only what those steps need, take the text as the answer to their question (ask only what it leaves open), write what they write, and when the change reaches the page (a Theme, a page setting, a section's title or flags), fill and publish it as in **Page** and **Publish** of Write: the page is replaced, so it is filled, translated and declared exactly as in a full setup. Report what changed. Text that matches no step: ask what to change rather than running the full setup.

## Sources

A source is a place the Sync reads origin items from, declared once: a `[[source]]` entry in `organizer.toml` (`id`, `tools` as `{server, tool}` entries, `prompt` = `sources/<id>.md`) and that file, written as prose for the agent that reads the source:
- **Ask:** how to ask the tools for what is new since a time, with the time as the one input. A pull request source holds two asks: the list since the cursor, and the full read of one PR (diff, comments, participants).
- **Returns:** what an item holds, as SKILL.md step 3 names the fields. A source that returns its whole window every Sync run, such as a calendar, says so. A pull request source emits the **Pull request** terms of the [glossary](https://github.com/EmblaTech/claude-plugins/blob/main/docs/organizer/glossary.md) and names in one line which host fields they come from.
- **Quirks:** a link to the provider's gotchas reference, kept in the project; the quirks themselves stay out of the file.
- **Local only**, when a cloud run cannot reach it.

A folder outside the repo is a git source when it is a repo, otherwise a folder source read by file modified time. A source only one section wants is declared the same way. Done when every source a section wants has an entry and a file.

## Theme

The **Theme** is `theme.css`, token values only; the **Style source** is the DESIGN.md it was made from. Both sit in `.claude/organizer/`; the skill ships the default pair, `theme.css` and `DESIGN.md`, in its own folder. A Theme is generated only here: every publish, by setup or a routine, takes the committed `theme.css` as it is.

- **Style source.** The default: this skill's pair, copied as is. A Refero style: the user pastes what its **Copy .md** button gives, or the Refero MCP supplies it when connected; these are the two routes, since Refero builds the file in the browser and its robots.txt blocks AI crawlers. A DESIGN.md link: fetch the raw DESIGN.md (a style's page usually links it). A local file or a paste: read it. Save it unchanged as `DESIGN.md`.
- **Map, don't copy.** Sources differ in shape: YAML front matter with the spec's groups (`colors`, `typography`, `rounded`, `spacing`), or Markdown tables plus a CSS block with names of their own (`--color-canvas`, `--text-body`) and values that are not CSS (`48-80px`). Fill each token in the `Required tokens` list in `base.css` with the source value that plays that role; type maps by role at the dashboard's scale (the page headline is a heading near 22px, never a 48px display). A role the source lacks (often `primary-container`, the emphasis weight) is derived in the source's palette and marked derived.
- **Semantic colours** (`warning`, `error`, `ok`, `ai`) mean a state, never decoration: take the source's status colours where it has them; derive the rest at the Theme's own chroma and lightness, muted in an achromatic source and saturated in a colourful one, and mark them derived. In an achromatic source `ai` may be `primary`.
- **Dark.** A colour takes its source's dark counterpart (a `<name>-dark` token, or a dark-role token such as `surface-dark` or `on-dark`); a colour with none is derived (same hue, lightness inverted for a dark surface) and marked derived. The dark blocks hold only the colours, plus the shadow when it differs; type, rounded and spacing live in the light block.
- **Contrast.** Every text colour holds WCAG AA 4.5:1, light and dark, on every background `base.css` puts it on, its `color-mix()` tints included. A failing value moves in lightness within its hue until it holds; report each as source value → Theme value.
- **Fonts** from Google Fonts only, the one font host the artifact loads, in one `@import` with every family and weight the Theme uses. A family missing there gets its nearest Google Fonts match, reported to the user.
- **Shape** as the skill's `theme.css`: the import; a comment naming the Style source and every derived value and font substitution (a derived value also gets `/* derived */` beside it); the light `:root` block; the colours in both dark blocks.

Done when `OZ_THEME=.claude/organizer/theme.css node --test "<this skill's folder>/page.test.mjs"`, run from the project root, passes (it checks the Theme contract on that file as well as on the skill's default), every contrast pair holds, and the user has the list of derived values, contrast fixes and font substitutions.
