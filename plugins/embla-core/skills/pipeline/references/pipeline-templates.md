## `bitbucket-pipelines.yml` Template

Read the exact content to write from [references/bitbucket-pipelines-template.yml](bitbucket-pipelines-template.yml) — it's the raw file, copy it verbatim, do not retype it from memory. Write it to the project repo root when `bitbucket-pipelines.yml` does not exist.

**Why this step exists (single step, top to bottom):**
- `trap 'RC=$?; FAIL_CMD="$BASH_COMMAND"; FAIL_LINE="$LINENO"; on_error "$RC"' ERR`, registered as the very first thing the script does, before `npm install` — capturing `$?` into `RC` as the trap's first action matters: by the time a later statement in the trap ran, `$?` would reflect that statement's own (successful) exit status, not the command that actually triggered the trap — Bitbucket runs a step's whole `script:` list as one continuous shell session (this is already relied on elsewhere in this same file: the `.pipeline-env` heredoc written partway through is read by a `su` call several list entries later), so a trap declared first stays active for every later command in the step, not just the ones after it in the same list entry. If `npm install`, the plugin `git clone`, `useradd`, or `chown` fails, this trap is what catches it — previously, an earlier failure like this killed the whole step with no synthesized explanation anywhere, because there was no second step left to run and report it.
- `useradd -m claudeuser` — Claude Code cannot run as root in a pipeline container
- `git clone ... /tmp/plugins` — embla-core skills are not bundled in the container; must be cloned at runtime from the official plugin repo
- `git -C /tmp/plugins checkout <commit>` — pins the plugin checkout to a known-good commit instead of tracking `main` directly, so a push to `embla-claude-plugins` (accidental or malicious) can't silently change what every consuming pipeline executes on its next run. This pin does not auto-update — see "Updating the pinned plugin commit" below.
- `cat > /home/claudeuser/.pipeline-env <<PIPELINE_ENV ... PIPELINE_ENV` — writes only the specific env vars Claude needs to a 600-permission file via a heredoc, not by passing secrets as CLI arguments to a command (as `printf '...' "$SECRET"` would) — a heredoc's expanded content flows through the shell into `cat`'s stdin, never into any process's argv, so nothing appears in `/proc/PID/cmdline`. `${VAR@Q}` (bash parameter transform) applies the same shell-safe escaping as `printf %q` without needing to hand the value to a command as an argument
- `chown -R claudeuser:claudeuser docs/reviews /home/claudeuser /tmp/plugins` — `claudeuser` only needs write access to where `pr-review`'s local review file is saved (`docs/reviews`), its own home directory, and the cloned plugin checkout — not the whole tracked repo, so a hijacked review session can't overwrite and push source changes
- `apt-get remove -y curl wget python3 netcat-traditional` — reduces attack surface before running Claude in the container; guards against prompt-injection attempts that try to exfiltrate data via those tools. Reinstalling `curl`/`jq` later (in `report_and_exit`, after `claude` has already exited) is safe precisely because the untrusted-content-processing phase is over by then — there's no live Claude session sharing that container anymore for a reinstalled tool to be abused by
- The `( set +e ... ) || true` Jira pre-fetch block — resolves the issue key from the PR title or source branch, then fetches the issue with `curl` (REST **v2**, so `description` is plain text rather than ADF JSON) into `docs/reviews/jira-issue.json`, which `pr-review`'s Phase 2.4 reads instead of calling a Jira MCP tool. It runs here because it must precede `apt-get remove -y curl`. Why bother: `--allowedTools` is a *permission* filter, not a loading filter — an MCP server's entire tool schema is sent into context whether or not any of its tools may be called, so the Jira server was contributing five tool schemas to every turn to serve one read. Removing it drops those schemas, one `npx` cold start per run, and `ATLASSIAN_API_TOKEN`/`ATLASSIAN_USER_EMAIL`/`ATLASSIAN_SITE_NAME` from the review process's environment. The whole block runs in a subshell with `set +e` and is followed by `|| true` specifically so the active `ERR` trap cannot fire inside it: a missing ticket, a revoked Jira token, or a 404 must degrade the review to "no Jira context" (which `requirement` already handles) and never fail the build. `mv` from `/tmp` only after `jq -e '.key'` confirms the payload parsed, so a partial write never lands where Phase 2.4 would trust it
- `su claudeuser -c "... claude ..." | tee docs/reviews/pr-review-cost.json` — runs Claude Code as non-root, sourcing only the allowlisted vars from `.pipeline-env` (not the full parent environment) and deleting that file immediately afterward. `--output-format json` makes `claude -p` emit a single JSON envelope instead of a plain-text transcript; `tee` captures that JSON to a file for `report_and_exit` to read while still surfacing it in the build log. **`total_cost_usd` and `usage` do not have the same scope:** `total_cost_usd` is the whole-session total and does include every subagent dispatch, but the `usage.*` token counts cover the **main session only** — measured on a live run, `usage` reported 2,991 input tokens against a $4.24 bill, i.e. under 1% of the real input volume. Never present the token counts as if they explain the dollar figure
- `--model claude-sonnet-4-6` — pinned to Sonnet 4.6; `--model sonnet` resolves to Sonnet 5, which flags security code-review prompts under its cybersecurity safeguard
- `--allowedTools` — restricts Claude to only the tools needed for PR review; replaces `bypassPermissions` to mitigate prompt-injection risk. `Bash` itself is further scoped to `Bash(git fetch:*),Bash(git diff:*)` — the only shell commands `pr-review` actually runs — instead of a bare `Bash`, so a prompt injection in a reviewed PR's diff/description can't get an arbitrary command executed. `mcp__atlassian__jira_get` is absent because there is no Jira MCP server any more (see the pre-fetch bullet above). `ANTHROPIC_API_KEY`/`BITBUCKET_API_TOKEN` remain in the process env for the lifetime of the `claude` process even after `.pipeline-env` is deleted; the Atlassian credentials no longer do, since only the root-shell pre-fetch needs them
- `--plugin-dir` — points Claude Code at the cloned skill files. `--mcp-config .mcp.json` — explicitly loads MCP config from the project root
- `post_comment()`'s `printf 'user = "%s:%s"\n' "$BITBUCKET_EMAIL" "$BITBUCKET_API_TOKEN" | curl -s -K -` — passes Bitbucket Basic Auth credentials to curl via stdin (`-K -` reads config from stdin), not as a `-u user:pass` command-line argument, which would put the token in argv and visible to any other process on the container via `/proc/PID/cmdline`. Uses `$BITBUCKET_EMAIL`, not `$BITBUCKET_USERNAME` — the latter is scoped to git authentication only (an account handle, not an email) and fails this REST call with `"API token must be used with an atlassian registered email"`
- `-o /dev/null -w "Comment $2: HTTP %{http_code}\n"` — discards the API response body instead of letting it print to the build log; the body isn't needed and contains PII (reviewer display name, account ID, avatar URL)
- `COST=$(printf '%.2f' "$RAW_COST" ...)` plus wrapping every numeric value in the posted comment in backtick code spans — `total_cost_usd` from `claude --output-format json` is a raw float commonly serializing with 6-7 fractional digits (e.g. `3.3166899`); an unrounded digit run that long is exactly what Bitbucket's markdown renderer auto-linkifies as a commit-hash reference (hit in live testing — `3166899` rendered as a dead link to a nonexistent commit). Rounding removes most of the risk; the backtick code spans (exempt from that auto-linking) remove the rest
- `jq -r '.total_cost_usd'` / the summed input expression / `.usage.cache_read_input_tokens` / `.usage.output_tokens` — extracts only numeric fields from the artifact JSON. Never extract free-text fields (e.g. anything containing the PR title/description) into a shell variable that gets interpolated into a command line — numeric-only extraction is what keeps this safe from injection via a crafted PR. Input is summed as `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` because `input_tokens` alone counts only uncached tokens, which on a cache-warm run is a small fraction of what was actually sent; cache reads are also reported on their own so a run's cache effectiveness is visible rather than hidden inside the total
- `REVIEW_EXIT=${PIPESTATUS[0]}` — captures `claude`'s real exit code from the pipe, not `tee`'s (which is almost always `0`) — same reasoning as before, just no longer needed to survive a step boundary. Not trustworthy alone as a gate verdict, though: it reflects harness completion, not the agent's conclusion (see [pipeline-mode.md](../../pr-review/references/pipeline-mode.md) → "Exit Code Logic")
- The `gate-result.json` check right after overwrites `REVIEW_EXIT` with the file's `exit_code` when present — written by Phase 7 as `pr-review`'s last action. Missing is still correct either way: a crash already left `REVIEW_EXIT` non-zero via the `ERR` trap, and a skipped run left it `0` with nothing wrong
- `report_and_exit "$REVIEW_EXIT" "review"` — the single reporting path, whether reached here (the expected end of the script) or via `on_error` (an earlier command's failure). It first unconditionally logs that it's starting, with the exit code and mode — this line cannot be skipped by anything that fails afterward, including the next line. It:
  1. Reinstalls `curl`/`jq` (removed above, safe to bring back now) via `apt-get update && apt-get install`, with a retry-with-update fallback if the first attempt fails — the plain `apt-get install` this replaced could fail with "Unable to locate package" on this image with no preceding `apt-get update`, which would have killed this whole function with no comment posted; the final `|| echo` on the fallback attempt means even a persistent apt failure logs a warning and continues rather than aborting
  2. Checks whether `docs/reviews/report-comment-id.txt` (written by `pr-review`'s Step B — see [output-format.md](../../pr-review/references/output-format.md)) is a bare numeric id (never trusted as free text — a non-numeric or empty value is treated as absent) and whether `docs/reviews/pr-review-cost.json` is present and valid JSON with a `total_cost_usd` field — this, not the raw exit code, decides whether the review actually finished. A crash and a real gate failure (`pr-review`'s own contract: exit `1`) can both leave the same exit code behind; only these artifacts prove which one happened
  3. If both are valid: fetches the existing summary comment by id, appends the cost line (built with `jq -n --arg`, never hand-interpolated, so nothing in the existing comment's own text — even backticks or quotes — can break the JSON payload), `PUT`s it back. If the exit code is non-zero, also prints the gate diagnostic to the build log (pointing at that same, now cost-annotated, comment) — this is a log-only message, not a second post; the comment itself only ever gets the one cost-line patch, applied unconditionally above regardless of exit code
  4. If the cost JSON is valid but there's no comment id **and the exit code is `0`**: this is a legitimate skip, not a failure — `pr-review`'s Phase 1 eligibility check skips a draft PR, a closed/merged PR, or a re-run with no new commits since the last review, all without ever reaching Step B. Logs why nothing is being posted and exits `0` cleanly — no fallback comment, since there's nothing wrong to report
  5. Otherwise: this run never finished (a real crash, or a non-zero exit with no valid artifacts). Logs the specific known reason (the failing command + line from the trap, or just the raw exit code if the failure happened after setup) and posts a **new** fallback comment instead, since there's no summary comment to patch. Forces a non-zero exit even if the raw code was somehow `0`, since an incomplete-and-unexplained run is never a pass. Before composing that fallback, it also pulls `is_error`, `subtype`, and `result` out of `docs/reviews/pr-review-cost.json` if the file exists and parses — `claude --output-format json` still writes this envelope on a hard failure (e.g. an Anthropic API auth/rate-limit/usage-cap rejection), just with `total_cost_usd: 0`, and the real error text sits in `.result` the whole time. Without this, that JSON only ever reached the build log as one giant unparsed line inside the `tee` output from the `claude` invocation above — never labeled, never surfaced in the PR comment — so a genuine API-side failure and an unrelated shell bug in this script both read as "$0.00, see the log" with no way to tell them apart. `is_error`/`subtype` are echoed to the build log (only when `is_error` is `true`, so a normal crash with no envelope at all doesn't print a spurious line), and `result` (truncated to 4000 chars) is echoed too and folded into the fallback comment body in a fenced code block, replacing the previous static "see the step log" text; `<no result field available — see the step log>` is the fallback text for when the file never existed at all, e.g. a crash before `claude` started. `result` reaches the comment only via `jq -n --arg`, never shell-interpolated, so the same injection-safety property as the cost-line patch above holds even though this field is free text rather than the numeric-only fields that patch extracts
  Posting is always wrapped in `|| echo "..."` — a transient posting failure (network blip, rate limit) never changes the real exit code, and the specific reason is always printed to the log *before* any posting attempt, so it's visible even if every post fails.
- The `report_and_exit`/`on_error` distinction (the function's second argument, `"review"` vs. `"infra"`) exists so a failure inside `report_and_exit` itself is never misread as a fresh review result: `on_error` always passes `"infra"`, which routes straight to the incomplete-run branch regardless of what `COMMENT_ID`/`COST_JSON_OK` happen to be. This is currently inert in practice (an infra failure always precedes artifact creation) but is load-bearing if this script is ever changed to add `-o pipefail` to the `su | tee` line — do not add that flag; it would make a real gate failure (exit `1`) route through the `ERR` trap as `"infra"` instead of the intended `"review"` path
- No `artifacts:` key anywhere in this template — that mechanism exists only to pass files between *separate* step containers. With one step, `report_and_exit` reads `report-comment-id.txt` and `pr-review-cost.json` directly off the same filesystem `pr-review` wrote them to.

### Updating the pinned plugin commit

The `git -C /tmp/plugins checkout <commit>` line pins to a specific commit because this repo has no version tags. When a change to `plugins/embla-core/skills/**` should reach pipelines (bug fix, new capability used by `--plugin-dir`, e.g. `pr-review`):

1. Get the new commit: `git ls-remote https://bitbucket.org/emblaftdev/embla-claude-plugins.git main`, or read `target.hash` from `GET /repositories/emblaftdev/embla-claude-plugins/refs/branches/main`, or check the Bitbucket UI.
2. Update the pinned commit in [references/bitbucket-pipelines-template.yml](bitbucket-pipelines-template.yml). This only affects future `/embla-core:pipeline setup` runs.
3. Existing repos with an already-generated `bitbucket-pipelines.yml` don't pick this up automatically — `setup`'s merge rules stop and do nothing if an `AI PR Review` step already exists (see Merge rules below). Each consuming repo needs to run `/embla-core:pipeline check`, which will flag the pinned commit as out of sync with the canonical template, then manually update their `bitbucket-pipelines.yml` to match.

### Merge rules — when `base_pipeline` is not `new`

If `base_pipeline = new`: skip these rules and write the full template from scratch (see SKILL.md Phase 2).

Operate on `base_pipeline` as resolved by Phase 0. Never use the raw local file directly.

Only one step (`AI PR Review`) is inserted — there's no second step to coordinate with anymore.

1. Scan `base_pipeline` for a step named `AI PR Review` (our own step, from a prior run). If found → stop: `"AI PR Review step already present — no changes made."` (a repo already running the old two-step template also has an `AI PR Review` step present, so `setup` stops there too rather than silently doing nothing useful — that repo needs `/embla-core:pipeline check` to detect the old template and guide migration to the new single-step one, not another `setup` run; see `check`'s migration-detection message)
2. List every other step name found under `pull-requests:` (any pattern) and show them to the developer before inserting — do not try to heuristically guess from a step's name or script whether it already performs code/PR review, ask directly instead, consistent with "never silently pick" (Phase 0):
   ```
   Existing pull-request pipeline steps: {step names, or "none" if empty}.
   Does any of these already run a code/PR review? Proceed with adding AI PR Review anyway? (yes / cancel)
   ```
   - `yes` → proceed to insertion
   - `cancel` → stop: `"Cancelled. No files were changed."`
3. Locate the insertion point:

| What exists in `base_pipeline` | Action |
|---|---|
| `pull-requests:` with `'**':` pattern | Append our step as the last step under `'**':` |
| `pull-requests:` with only named patterns (e.g. `feature/**`) | Add a new `'**':` pattern block with our step after the existing patterns |
| `pull-requests:` block exists but empty | Add `'**':` pattern block with our step inside it |
| No `pull-requests:` block | Append the full `pull-requests:` block (our step) at the end of the file |

4. Never delete or modify any existing step.
5. After computing the merge in memory, write it to disk and print the result (see Phase 2 in SKILL.md — no confirmation gate).

## `bitbucket-pipelines-ai-develop-template.yml` Template

Read the exact content to write from [references/bitbucket-pipelines-ai-develop-template.yml](bitbucket-pipelines-ai-develop-template.yml) — it's the raw file, copy it verbatim, do not retype it from memory. This defines a `custom` pipeline (`pipelines: custom: ai-develop:`), triggered manually or by a Jira automation rule — not a `pull-requests:` pattern like `AI PR Review` — so it is written as its own separate pipeline block, never merged into the `pull-requests:` block.

**Why this step exists (differences from the `bitbucket-pipelines.yml` / `AI PR Review` template):**
- `curl`/`jq` are **not** removed before the `claude` invocation here — unlike `pr-review`'s `apt-get remove -y curl wget python3 netcat-traditional`, this template only removes `wget python3 netcat-traditional`. `develop-auto` itself needs `git push` and the live `atlassian`/`bitbucket` MCP servers for the whole autonomous-dev session, not a one-shot read, and this template's own `report_and_exit` fallback needs `curl`/`jq` available immediately if a crash happens *before* `develop-auto` gets a chance to report its own outcome. `curl` was never removed in the first place, so there's nothing to reinstall for it; `jq` *is* installed inside `report_and_exit` itself (it isn't present on the base `node:24` image at all, removed or not) — unlike `pr-review`'s template, which only ever reinstalls what it earlier removed.
- `wget`/`python3`/`netcat-traditional` are still removed — same reasoning as `pr-review`: the Jira ticket body and its comments are untrusted content the agent reads over the life of the session, so the same prompt-injection/exfiltration attack-surface reduction still applies.
- The `atlassian` MCP server (`@aashari/mcp-server-atlassian-jira`, added to `mcp-template.json` — see below) is loaded here, unlike `pr-review`, which pre-fetches the Jira issue once via `curl` and never starts a Jira MCP server at all. `develop-auto` isn't a single read — over the life of an autonomous dev session it fetches the story, posts comments, transitions status, and updates fields — so a live MCP server is the right shape here, not a one-shot pre-fetch.
- `report_and_exit`'s `is_error != true` branch does two things, since `develop-auto` already posts its own Jira comment for both outcomes it can reach unassisted — a successful run and a graceful, deliberate abort (e.g. missing `SPRINT_NUMBER`) — and this wrapper must relay Bitbucket a verdict without posting a second, generic one on top:
  1. Decides whether to trust that comment was posted at all, via `is_error` — not just whether the file parses, since `claude --output-format json` still writes a valid envelope on a hard crash (max turns, context exhaustion, an API failure) with `is_error: true` and the explanation in `.result`. Skip posting only when `is_error` is `false` or absent (older `claude`); otherwise fall back to `post_jira_comment`, folding `.result` (truncated to 4000 chars) in, same as `pr-review`'s own fallback
  2. Overwrites `CODE` with `docs/reviews/develop-auto-result.json`'s `exit_code` when present — `is_error` alone can't tell success from abort, since both end in a normal `end_turn`; this file, written by `develop-auto` itself as the last thing it does either way, can. Missing leaves `CODE` as the raw `DEV_EXIT`
- Before any of the setup work (`npm install`, `useradd`, cloning the plugin repo) runs, the script validates `JIRA_ISSUE_KEY` (must match `^[A-Z][A-Z0-9]+-[0-9]+$`), `COMMENTER_ACCOUNT_ID` (must match `^[A-Za-z0-9:_-]*$`, empty allowed), and `SPRINT_NUMBER` (digits only, empty allowed) — and aborts immediately (plain `exit 1`, bypassing `report_and_exit` entirely, deliberately not attempting a Jira comment since an unvalidated `JIRA_ISSUE_KEY` isn't confirmed to be a real, safe key to comment on) if any fails. This matters because all three values get interpolated into the single string handed to `su claudeuser -c "..."`, which is *re-parsed as a shell command* by the inner shell `su` starts — unlike, say, `post_jira_comment`'s use of `$JIRA_ISSUE_KEY` inside a `curl` URL argument (not re-parsed by anything), a crafted value reaching the `su -c` string could break out of the intended command and execute arbitrary shell. These are the only three pipeline variables that reach that interpolated string, so they're the only three validated.
- `git config --global user.name`/`user.email`, set inside the `.pipeline-env` heredoc content itself (so they run as `claudeuser` when that file is later sourced, by which point `HOME=/home/claudeuser` — the export immediately above them in the same heredoc — has already taken effect in that same shell) — every `git commit` this skill runs (Steps 5b, 6, 7 of `develop-auto`) needs a configured identity, and `HOME=/home/claudeuser` means any gitconfig baked into the underlying image is unreachable regardless. The bot identity used is `"AI Autonomous Dev" <ai-autonomous-dev@noreply.embla.asia>` — deliberately non-human and no-reply-style so commit authorship is never mistaken for a real developer's.
- `git config --global credential.helper`, set right after the identity lines in that same heredoc — `git push` in `develop-auto`'s Step 7 needs the same Bitbucket credentials the plugin `git clone` step already used, and `su claudeuser -c "..."` only ever sees the variables explicitly exported into `.pipeline-env` (not the full parent environment, by design — see the credential-heredoc bullet in the `bitbucket-pipelines.yml` section above), so `BITBUCKET_USERNAME` is now also exported into this heredoc (alongside the already-exported `BITBUCKET_API_TOKEN`) specifically so this credential helper — and therefore `git push` — has something to authenticate with.
- `chown -R claudeuser:claudeuser . /home/claudeuser /tmp/plugins` — note the bare `.` (the whole repo working directory), broader than `pr-review`'s narrower `chown -R claudeuser:claudeuser docs/reviews /home/claudeuser /tmp/plugins`. This is deliberate, and the most security-relevant divergence from the `pr-review` template: `develop-auto` edits and commits source across the repo (implementation code, dev-plan docs, test files), not just `docs/reviews/`, so `claudeuser` genuinely needs write access to the whole tree to do its job. `pr-review` never writes source, so it never needed more than its own output directory — this template can't make the same narrow claim.
- The pinned plugin commit (`git -C /tmp/plugins checkout <commit>`) uses the same mechanism as the `AI PR Review` template — see "Updating the pinned plugin commit" above — but is an independent pin: it doesn't need to match the `AI PR Review` template's pinned commit, and the two aren't bumped together. Bump this template's pin only when a change touches the skill files this pipeline actually runs (`develop-auto`'s, primarily); bump `bitbucket-pipelines-template.yml`'s pin only when a change touches `pr-review`'s files.

**New required Bitbucket pipeline variables** (beyond the existing set already required by the `AI PR Review` template — `ANTHROPIC_API_KEY`, `BITBUCKET_API_TOKEN`, `BITBUCKET_USERNAME`, `BITBUCKET_WORKSPACE`, `BITBUCKET_EMAIL`):
- `JIRA_ISSUE_KEY` — the ticket this run develops; supplied by whatever triggers the custom pipeline (a Jira automation rule, or a manual run).
- `COMMENTER_ACCOUNT_ID` — the Atlassian account id of whoever triggered the run. May be blank — `develop-auto` handles a blank value itself.
- `SPRINT_NUMBER` — **required, not optional.** The pipeline's checkout starts on the repo's default branch, which carries no parseable sprint prefix (unlike a feature branch a developer checked out themselves), so `develop-auto`'s branch-name generation (its Step 4) falls back to this variable to build the `s{sprint}/feature/{JIRA-ID}/...` branch name. A missing value is one of Step 4's own abort conditions.

`ATLASSIAN_SITE_NAME` and `ATLASSIAN_API_TOKEN` are **reused as-is** from the existing `AI PR Review` template's requirements (where they back that step's `curl` Jira pre-fetch) — nothing new is introduced for those two; they're just consumed differently here, by the `atlassian` MCP server instead of a `curl` pre-fetch.

## `.mcp.json` Template

Read the exact content from [references/mcp-template.json](mcp-template.json) — it's the raw file, copy server blocks verbatim from it, do not retype either from memory. This file is a **two-block catalogue**, not a single verbatim template to write in one shot: when `.mcp.json` does not exist yet, copy only the `bitbucket` block to the project repo root. The `atlassian` block is never written this way, even for a brand-new file — it is added only by Phase 2.5's `yes` path (SKILL.md), whether `.mcp.json` is new or pre-existing at that point.

All `${VAR_NAME}` tokens are written exactly as shown — do not substitute values from `settings.json`. These are canonical variable names users must set in Bitbucket pipeline variables. The `env` section overrides the inherited environment for that server.

**Two server blocks, used by different pipelines.** `bitbucket` is used by every consumer of this template. `atlassian` (`@aashari/mcp-server-atlassian-jira`) exists for the `ai-develop` custom pipeline (see the `bitbucket-pipelines-ai-develop-template.yml` section above), which needs a live Jira MCP server across the whole autonomous dev session — not the one-shot `curl` pre-fetch `AI PR Review`'s step uses. `AI PR Review` itself still doesn't call `atlassian` at all: it pre-fetches the Jira issue with `curl` before Claude starts (see the pre-fetch bullet under "Why this step exists"), because for that one-read use case, an MCP server's full tool schema being loaded into every context regardless of `--allowedTools` was pure overhead.

**Why two separate tokens still exist:** `BITBUCKET_API_TOKEN` is a Bitbucket App Password (scoped to Bitbucket only). `ATLASSIAN_API_TOKEN` is an Atlassian API token from id.atlassian.com (scoped to Jira/Confluence). They are different credential types and cannot be used interchangeably. Both are still required Bitbucket variables — the Bitbucket one reaches the MCP server under the `ATLASSIAN_API_TOKEN` key name that package expects; the Atlassian one is used only by the step's `curl` pre-fetch and never enters the review process's environment.

### Merge rules (file already exists)

- Parse existing `.mcp.json` — if invalid JSON: stop and print `"Cannot parse existing .mcp.json — fix manually before retrying."`
- For the `bitbucket` server: if the key already exists → skip it, print that it was skipped
- Add it only if missing
- Never overwrite existing server config
- If an `atlassian` (Jira) server block exists from an older setup, check whether this repo's `bitbucket-pipelines.yml` has an `ai-develop` custom pipeline step (`ai_develop_present` from Phase 0) before deciding what to print — the block's presence is expected and harmless when `ai-develop` is installed, since that pipeline needs it:
  - `ai_develop_present` true → leave it in place; no warning needed, this is exactly what should be there.
  - `ai_develop_present` false → leave it in place (never delete a server block the user may rely on elsewhere) but print: `"Existing 'atlassian' server found, but this repo has no ai-develop pipeline step — it may be left over from an old setup or an unused manual customization, and costs five unused tool schemas per review context if truly unused. Remove it manually if you don't need it, or run /embla-core:pipeline setup and opt into ai-develop if you do."`
