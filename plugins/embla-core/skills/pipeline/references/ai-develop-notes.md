# ai-develop pipeline notes

Read by `setup` Phase 2.5 and by `check` when a `pipelines: custom: ai-develop:` block exists. ai-develop is Bitbucket-only and unchanged by the multi-provider work: its template still clones the plugins from Bitbucket with credentials and carries its own pin, and it is the only consumer of the `atlassian` block in `mcp-template.json`.

## `bitbucket-pipelines-ai-develop-template.yml`

Read the exact content to write from [references/bitbucket-pipelines-ai-develop-template.yml](bitbucket-pipelines-ai-develop-template.yml) — it's the raw file, copy it verbatim, do not retype it from memory. This defines a `custom` pipeline (`pipelines: custom: ai-develop:`), triggered manually or by a Jira automation rule — not a `pull-requests:` pattern like `AI PR Review` — so it is written as its own separate pipeline block, never merged into the `pull-requests:` block.

**Why this step exists (differences from the `bitbucket-pipelines.yml` / `AI PR Review` template):**
- `curl`/`jq` are **not** removed before the `claude` invocation here — unlike `pr-review`'s `apt-get remove -y curl wget python3 netcat-traditional`, this template only removes `wget python3 netcat-traditional`. `develop-auto` itself needs `git push` and the live `atlassian`/`bitbucket` MCP servers for the whole autonomous-dev session, not a one-shot read, and this template's own `report_and_exit` fallback needs `curl`/`jq` available immediately if a crash happens *before* `develop-auto` gets a chance to report its own outcome. `curl` was never removed in the first place, so there's nothing to reinstall for it; `jq` *is* installed inside `report_and_exit` itself (it isn't present on the base `node:24` image at all, removed or not) — unlike `pr-review`'s template, which only ever reinstalls what it earlier removed.
- `wget`/`python3`/`netcat-traditional` are still removed — same reasoning as `pr-review`: the Jira ticket body and its comments are untrusted content the agent reads over the life of the session, so the same prompt-injection/exfiltration attack-surface reduction still applies.
- The `atlassian` MCP server (`@aashari/mcp-server-atlassian-jira`, added to `mcp-template.json` — see below) is loaded here, unlike `pr-review`, which pre-fetches the Jira issue once via `curl` and never starts a Jira MCP server at all. `develop-auto` isn't a single read — over the life of an autonomous dev session it fetches the story, posts comments, transitions status, and updates fields — so a live MCP server is the right shape here, not a one-shot pre-fetch.
- `report_and_exit`'s `is_error != true` branch does two things, since `develop-auto` already posts its own Jira comment for both outcomes it can reach unassisted — a successful run and a graceful, deliberate abort (e.g. missing `SPRINT_NUMBER`) — and this wrapper must relay Bitbucket a verdict without posting a second, generic one on top:
  1. Decides whether to trust that comment was posted at all, via `is_error` — not just whether the file parses, since `claude --output-format json` still writes a valid envelope on a hard crash (max turns, context exhaustion, an API failure) with `is_error: true` and the explanation in `.result`. Skip posting only when `is_error` is `false` or absent (older `claude`); otherwise fall back to `post_jira_comment`, folding `.result` (truncated to 4000 chars) in, same as `pr-review`'s own fallback
  2. Overwrites `CODE` with `docs/reviews/develop-auto-result.json`'s `exit_code` when present — `is_error` alone can't tell success from abort, since both end in a normal `end_turn`; this file, written by `develop-auto` itself as the last thing it does either way, can. Missing leaves `CODE` as the raw `DEV_EXIT`
- Before any of the setup work (`npm install`, `useradd`, cloning the plugin repo) runs, the script validates `JIRA_ISSUE_KEY` (must match `^[A-Z][A-Z0-9]+-[0-9]+$`), `COMMENTER_ACCOUNT_ID` (must match `^[A-Za-z0-9:_-]*$`, empty allowed), and `SPRINT_NUMBER` (digits only, empty allowed) — and aborts immediately (plain `exit 1`, bypassing `report_and_exit` entirely, deliberately not attempting a Jira comment since an unvalidated `JIRA_ISSUE_KEY` isn't confirmed to be a real, safe key to comment on) if any fails. This matters because all three values get interpolated into the single string handed to `su claudeuser -c "..."`, which is *re-parsed as a shell command* by the inner shell `su` starts — unlike, say, `post_jira_comment`'s use of `$JIRA_ISSUE_KEY` inside a `curl` URL argument (not re-parsed by anything), a crafted value reaching the `su -c` string could break out of the intended command and execute arbitrary shell. These are the only three pipeline variables that reach that interpolated string, so they're the only three validated.
- `git config --global user.name`/`user.email`, set inside the `.pipeline-env` heredoc content itself (so they run as `claudeuser` when that file is later sourced, by which point `HOME=/home/claudeuser` — the export immediately above them in the same heredoc — has already taken effect in that same shell) — every `git commit` this skill runs (Steps 5b, 6, 7 of `develop-auto`) needs a configured identity, and `HOME=/home/claudeuser` means any gitconfig baked into the underlying image is unreachable regardless. The bot identity used is `"AI Autonomous Dev" <ai-autonomous-dev@noreply.embla.asia>` — deliberately non-human and no-reply-style so commit authorship is never mistaken for a real developer's.
- `git config --global credential.helper`, set right after the identity lines in that same heredoc — `git push` in `develop-auto`'s Step 7 needs the same Bitbucket credentials the plugin `git clone` step already used, and `su claudeuser -c "..."` only ever sees the variables explicitly exported into `.pipeline-env` (not the full parent environment, by design — see rule I2 in `pipeline-rules.md`), so `BITBUCKET_USERNAME` is now also exported into this heredoc (alongside the already-exported `BITBUCKET_API_TOKEN`) specifically so this credential helper — and therefore `git push` — has something to authenticate with.
- `chown -R claudeuser:claudeuser . /home/claudeuser /tmp/plugins` — note the bare `.` (the whole repo working directory), broader than `pr-review`'s narrower `chown -R claudeuser:claudeuser docs/reviews /home/claudeuser /tmp/plugins`. This is deliberate, and the most security-relevant divergence from the `pr-review` template: `develop-auto` edits and commits source across the repo (implementation code, dev-plan docs, test files), not just `docs/reviews/`, so `claudeuser` genuinely needs write access to the whole tree to do its job. `pr-review` never writes source, so it never needed more than its own output directory — this template can't make the same narrow claim.
- The pinned plugin commit (`git -C /tmp/plugins checkout <commit>`) uses the same mechanism as the `AI PR Review` template — see "Updating the pinned plugin commit" in `hosts/bitbucket/notes.md` — but is an independent pin: it doesn't need to match the `AI PR Review` template's pinned commit, and the two aren't bumped together. Bump this template's pin only when a change touches the skill files this pipeline actually runs (`develop-auto`'s, primarily); bump the `hosts/*/template.yml` pins only when a change touches `pr-review`'s files.

**New required Bitbucket pipeline variables** (beyond the existing set already required by the `AI PR Review` template — `ANTHROPIC_API_KEY`, `BITBUCKET_API_TOKEN`, `BITBUCKET_USERNAME`, `BITBUCKET_WORKSPACE`, `BITBUCKET_EMAIL`):
- `JIRA_ISSUE_KEY` — the ticket this run develops; supplied by whatever triggers the custom pipeline (a Jira automation rule, or a manual run).
- `COMMENTER_ACCOUNT_ID` — the Atlassian account id of whoever triggered the run. May be blank — `develop-auto` handles a blank value itself.
- `SPRINT_NUMBER` — **required, not optional.** The pipeline's checkout starts on the repo's default branch, which carries no parseable sprint prefix (unlike a feature branch a developer checked out themselves), so `develop-auto`'s branch-name generation (its Step 4) falls back to this variable to build the `s{sprint}/feature/{JIRA-ID}/...` branch name. A missing value is one of Step 4's own abort conditions.

`ATLASSIAN_SITE_NAME` and `ATLASSIAN_API_TOKEN` are **reused as-is** from the existing `AI PR Review` template's requirements (where they back that step's `curl` Jira pre-fetch) — nothing new is introduced for those two; they're just consumed differently here, by the `atlassian` MCP server instead of a `curl` pre-fetch.

## `.mcp.json` `atlassian` block

`mcp-template.json` is a two-block catalogue. AI PR Review takes its `bitbucket` block from `hosts/bitbucket/mcp.json`; the `atlassian` block (`@aashari/mcp-server-atlassian-jira`) is added only by Phase 2.5's `yes` path, merged only if missing, never overwriting an existing `atlassian` block. Copy it verbatim with its `${VAR}` placeholders (C3).

When an `atlassian` block already exists:
- `ai_develop_present` true → leave it; this is what ai-develop needs.
- `ai_develop_present` false → leave it in place (it may serve something else) and print: `Existing 'atlassian' server found, but this repo has no ai-develop pipeline step — it may be left over from an old setup, and costs five unused tool schemas per review context if unused. Remove it manually if you don't need it, or run /embla-core:pipeline setup and opt into ai-develop if you do.`
