# Severity Rubric

One row per problem this skill can flag. Every finding gets exactly one severity (H/M/L) and exactly one marker (`[FIX]` / `[WARN]` / `[GAP]` / `[OK]`) — assign both at the point the subagent reports the finding, since that's where the context for the call exists, not at synthesis time.

This table is a worked-examples set, not a closed list — real audits turn up variations not enumerated here. When a finding doesn't match any row, classify it by the general rule for its category, not by leaving it unrated.

## General rule per category

- **Config & Permissions** — H if it silently breaks something or exposes a secret/credential; M if it's correct-but-misplaced config that only bites the team later (onboarding, drift); L if it's cosmetic or scoped to one person with no spillover.
- **Plugins & Skills Coverage** — H if a capability is enabled but actually absent (enabled-but-not-loaded, or a required MCP server that isn't connected/authorized with no working fallback) or an unvetted third party has standing tool access; M if a real, load-bearing part of the stack has no matching skill/plugin, an enabled plugin is clearly mismatched to the project, or an MCP server is unauthorized but an equivalent connector already covers it; L if the gap or mismatch is on something peripheral.
- **CLAUDE.md Structure** — H if there's no grounding at all where it's clearly needed (e.g. missing root file); M if a subfolder with genuinely distinct conventions lacks its own file, or an existing file is actively misleading after a major rewrite; L if it's a borderline placement call with low impact either way.
- **Automation Opportunities** — this category surfaces opportunities rather than breakage, so it rarely goes above M; M if a clearly repetitive, high-toil manual step would be removed by a hook/subagent/rule; L if the idea is plausible but speculative.

## Resolved rules (settle the open questions from the draft)

**Count escalation — yes, allowed.** An L-level issue that appears as an isolated instance stays L. The same issue clustered (e.g. a dozen missing read-only permissions on routine, safe operations, all contributing to constant approval-prompt friction) gets reported as a single M finding covering the cluster, not a dozen separate L rows. Use judgment on the threshold — "constant friction" is the bar, not a fixed count — and always name the actual count in the finding so the user can judge for themselves ("12 missing read-only permissions across file reads and read-only MCP calls").

**Delegated categories — rate the surface signal, don't do the delegated skill's job.** CLAUDE.md content review and deep automation design are out of scope for this skill, but a subagent that's already looking at a file for structural reasons will sometimes see something glaring (a CLAUDE.md that's obviously describing a directory structure that no longer exists; an automation opportunity that's obviously worth a hook, not just a maybe). Report that surface impression with a severity, but make explicit in the same finding that it's a first impression, not a full review, and repeat the pointer to the skill that owns the deeper pass (`claude-md-management:claude-md-improver` or `claude-code-setup:claude-automation-recommender`). Don't withhold a severity just because the category is delegated — that leaves the user with no signal on which delegated-follow-ups are urgent.

**Compliance floor — yes, secrets/credentials always floor at H.** Any finding that involves an exposed secret, token, API key, or credential-shaped string — or a permission/access-control misconfiguration that would let one — is H regardless of which category surfaced it or what the general category rule would otherwise say. This overrides every other row and general rule in this document. This skill doesn't attempt ISO 27001 conformance assessment itself; the floor exists because credential exposure is the one failure mode here with real, immediate, external consequences, not because this skill is compliance-aware more broadly.

## Markers

- **`[FIX]`** — safe, mechanical, reversible, and this skill can describe the exact edit. Reserved for what the "apply fixes" step is allowed to touch: moving a misplaced key between `settings.json` and `settings.local.json`, adding a missing read-only permission. Never used for plugin installs, CLAUDE.md edits, or anything touching a secret — those get `[WARN]` even when the fix seems obvious, because the cost of an auto-edit going wrong (deleting a real credential, mis-scoping a permission) is worse than leaving it for a human.
- **`[WARN]`** — real problem, but fixing it needs human judgment, a destructive step, or touches something this skill declines to auto-edit.
- **`[GAP]`** — something that should exist and doesn't: a missing skill/plugin for a detected stack element, a missing CLAUDE.md for a subfolder that needs one, a missing automation worth designing (design itself delegated onward).
- **`[OK]`** — explicitly verified correct. Include several in every report, not just problems — an all-findings report reads as "everything is broken" even when most of the setup is fine, and positive examples (correct settings placement, official-vendor plugin choices) are the pattern worth reinforcing.
